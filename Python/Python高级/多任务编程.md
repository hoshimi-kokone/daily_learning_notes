## 0.3、一句话记忆锚点

> **多进程** = 多开几个解释器，用 **内存隔离** 换 **真并行**。
> **多线程** = 一个解释器多个执行流，用 **锁** 换 **I/O 并发**，被 **GIL** 挡在 CPU 外。 
> **协程** = 一个线程内协作式切换，用 **await 主动让出** 换 **极低开销**，代价是 **全链路异步化**。

# 一、基础概念：并发、并行、同步、异步

## 1.1、并发 vs 并行

|  | 并发 Concurrency | 并行 Parallelism |
|---|---|---|
| 定义 | 多个任务在 **重叠的时间段** 内推进 | 多个任务在 **同一时刻** 真正同时执行 |
| 硬件要求 | 单核即可 | 必须多核 |
| 实现方式 | 时间片轮转 / 协作让出 | 多进程、多核线程、向量化 |
| 类比 | 一个人轮流做三件事 | 三个人各做一件事 |

> 常见误区：`多线程 = 并行`。在 CPython 里，多线程 **不是** CPU 并行，只是并发。

## 1.2、同步 / 异步 / 阻塞 / 非阻塞(四象限)

这四个词经常被混用，其实描述的是 **两个维度**：

- **同步 / 异步**：谁负责通知结果？——调用方主动等(同步) vs 被调用方通知(异步)
- **阻塞 / 非阻塞**：调用返回前，调用方线程是否被挂起？一挂起(阻塞) vs 立即返回（非阻塞）

| 组合 | 含义 | Python 对应 |
|---|---|---|
| 同步阻塞 | 调用后线程挂起直到结果返回 | `requests.get()`、`time.sleep()`、普通函数调用 |
| 同步非阻塞 | 立即返回，需轮询结果 | `socket.setblocking(False)` + `select` |
| 异步非阻塞 | 立即返回，完成后回调 / 唤醒 | `asyncio`、`await`、Twisted |

> **协程的被指就是 “异步非阻塞”**：`await` 处让出 CPU，事件循环去跑别的，I/O 完成后唤醒。

## 1.3、上下文切换成本(量级参考)

| 切换类型 | 开销量级 | 触发者 |
|---|---|---|
| 协程切换 | ~100 ns (函数调用级) | 用户代码 (`await`) |
| 线程切换 | ~1-10 $\mu s$ | 操作系统内核 |
| 进程切换 | ~10-100 $\mu s$ + TLB/缓存失效 | 操作系统内核 |

> 结论：并发量越大，越应该往“轻量”的方向选。1 万并发用线程是灾难，用协程是常态。

## 1.4、CPU 密集型 vs I/O 密集型

```python
# CPU 密集型：一直在算，从不主动让出
def cpu_bound(n: int) -> int:
    total = 0
    for i in range(n):
        total += i * i
    return total

# I/O 密集型：大部分时间在等
def io_bound(url: str) -> int:
    import requests
    return len(requests.get(url, timeout=30).content)
```

**判定方法**：用 `cProfile` 或 `py-spy` 看时间花在哪。**经验法则**：如果单任务耗时里有 > 70% 是在等 (网络、磁盘、数据库、锁)，就是 I/O 密集。

## 1.5、Amdahl 定律(为什么加核不一定变快)

```
加速比 S(n) = 1 / (P/n + (1-P))
    P   = 可并行部分比例
    n   = 核数
    1-P = 串行部分比例
```

| 可并行比例P | 4 核加速比 | 16 核加速比 | 理论上限 |
|---|---|---|---|
| 50% | 1.6x | 1.9x | 2x |
| 90% | 3.1x | 6.4x | 10x |
| 95% | 3.5x | 9.1x | 20x |
| 99% | 3.9x | 13.9x | 100x |

> 实践含义：多进程加速比上不去，先查 **串行部分**（数据序列化、结果汇总、启动开销），别急着加核。

## 1.6、三种模型总对照

| 维度 | 多进程 | 多线程 | 协程 |
|---|---|---|---|
| 执行单元 | 独立进程 | 进程内线程 | 线程内协程 |
| 内存空间 | 独立 | 共享 | 共享(同一线程) |
| 调度者 | OS(抢占) | OS(抢占) | 事件循环(协作) |
| 切换开销 | 大 | 中 | 极小 |
| 单实例内存 | 数十 MB | ~8 MB 栈 | 数 KB |
| CPU 并行 | 并行 | 不并行(GIL) | 不并行 |
| I/O 并发 | 并发，但浪费 | 并发 | 并发 |
| 数据共享 | 难(序列化) | 易(需加锁) | 极易(无需锁) |
| 崩溃影响 | 隔离 | 全挂 | 全挂 |
| 调试难度 | 高 | 高(竟态) | 中(调用栈断) |
| 最大并发量级 | 核数级 | 数百~数千 | 数万~数十万 |

## 本节要点

1. 并发 ≠ 并行；CPython 多线程不并行。
2. 协程 = 异步非阻塞；`await` 是主动让出
3. 选型第一问永远是：**CPU-bound 还是 I/O-bound**?
4. 加核前先算 Amdahl，串行部分决定天花板。

# 二、GIL：Python 多任务的总开关

## 2.1、GIL 是什么

**GIL(Global Interpreter Lock)** 是 CPython 解释器里的一把全局互斥锁：

> **同一进程内，同一时刻只允许一个线程执行 Python 字节码**

注意措辞：限制的是“执行 **Python 字节码**”，不是“执行线程”，也不是“等待 I/O”。

## 2.2、为什么存在

CPython 用 **引用计数** 做内存管理，`ob_refcnt` 的增减必须原子。如果多个线程同时改引用计数：

- 加锁粒度到每个对象 -> 锁竞争爆炸，单线程性能下降
- 全局一把大锁 -> 实现简单，单线程快，C 扩展兼容性好。

Guido 当年选了后者。这是 **工程妥协**，不是设计失误。

## 2.3、什么时候释放 GIL (关键！)

| 场景 | 是否释放 | 说明 |
|---|---|---|
| `time.sleep()` | 释放 | 内部是条件变量等待 |
| `socket.recv/send` | 释放 | 网络 I/O 前后释放 |
| `file.read/write` | 释放 | 磁盘 I/O |
| 网络/数据库驱动 (`requests`、`pymysql`) | 释放 | 底层 socket 操作 |
| `numpy`/`pandas` 的 C 运算 | 释放 | C 扩展主动 `Py_BEGIN_ALLOW_THREADS` |
| `hashlib`、`zlib`、`sqlite3` | 释放 | C 扩展主动 `Py_BEGIN_ALLOW_THREADS` |
| `print()` | 释放 | 内部有 I/O |
| **纯 Python 循环/运算** | 不释放 | **这是 GIL 唯一卡你的地方** |
| 解释器每执行 N 条字节码 | 周期性让出 | `sys.getswitchinterval()` 默认 0.005s |

> **重要结论**：`numpy` 的矩阵乘法、`hashlib` 的哈希、`zlib` 的压缩、**多线程的确能加速**，因为它们在 C 层释放了 GIL。不要盲目说：“Python 多线程没用来加速计算”。

## 2.4、实测：亲眼看到 GIL

```python
import threading, time
# threading：Python内置线程库，在同一个进程内创建多个执行流

N = 10_000_000      # 单个任务的循环次数 1 千万
TASKS = 4           # 任务数

# 纯 CPU 循环：不断把 n 减到 0，没有任何 IO (没有 sleep、读文件、网络)
def count():
    n = N           # 局部变量，每个线程各一份，无共享、无需锁
    while n > 0:
        n -= 1

# time.perf_counter()：高精度计时器，适合测代码耗时
# 基准：4 个任务「串行」跑
t0 = time.perf_counter() # 记录开始时间
for _ in range(TASKS):
    count()
serial = time.perf_counter() - t0 # 计算 4 串行开始到结束时间

# 4 个任务、4 个线程「并发」跑
# 生成 4 线程，句柄放在ths列表，每个线程运行count()
ths = [threading.Thread(target=count) for _ in range(TASKS)]
t0 = time.perf_counter() # 记录开始时间
for t in ths: t.start() # .start()启动线程，进入就绪状态，交给操作系统调度
for t in ths: t.join() # .join()主线程阻塞，等这个子线程全部执行完才继续往下走
threaded = time.perf_counter() - t0 # 计算 4 并行开始到结束时间

print(f"串行 {TASKS} 任务 : {serial:.2f}s  ({TASKS*N/serial/1e6:.1f} M ops/s)")
print(f"{TASKS} 线程 {TASKS} 任务: {threaded:.2f}s  ({TASKS*N/threaded/1e6:.1f} M ops/s)")
print(f"加速比           : {serial/threaded:.2f}x   ← ≈1.0 表示多线程毫无收益")
```

```ini
串行 4 任务 : 1.09s  (36.7 M ops/s)
4 线程 4 任务: 1.08s  (37.1 M ops/s)
加速比           : 1.01x   ← ≈1.0 表示多线程毫无收益
```

对照试验：把 `count` 换成 `time.sleep(1)`，4线程 $\sim$ 1秒。差异的来源就是 GIL 是否释放。

|---|---|---|

## 本节要点

1. GIL 限制的是“执行 Python 字节码”，不是“线程存在”
2. **I/O 会释放 GIL** -> 多线程对 I/O 有效

# 三、多进程 `multiprocessing`

## 3.1、原理与适用

每个进程有 **独立的 Python 解释器和内存空间**，所以：

优点：

- 完全绕开 GIL，能在多核上真并行
- 一个进程崩溃不影响其他

缺点：

- 内存开销大(每个进程 20-40 MB 起步)
- 数据交换必须序列化(pickle)，大对象很慢
- 启动慢(spawn 方式要重新导入模块)

**决策**：CPU 密集型首选；需要隔离性时首选。

## 3.2、最小示例：Process

```python
import multiprocessing as mp  # 导入多进程库，别名 mp
import os, time # os，用来拿进程 ID；time，计时

# 每个进程都会独立执行这个计算，不受 GIL 限制，可以多核并行
def worker(name: str, n: int) -> None:
    # os.getpid()：当前子进程自己的进程id
    # os.getppid()：parent pid，父进程的 id(也就是主进程)
    print(f"[{name}] pid={os.getpid()} 父={os.getppid()}")
    print(f"[{name}] 结果={sum(i * i for i in range(n))}") # CPU 密集计算，算平方和，用来占 CPU 核心

# Windows/macOS 默认 spawn 创建子进程：
# 子进程会重新启动一个 Python 解释器，再次加载当前脚本
# 如果不加这个判断：脚本顶层代码会反复新建子进程 -> 无限递归炸机
# Linux fork 模式虽然不一定崩，但规范写法必须带上
if __name__ == "__main__":          # ★ 必须
    t0 = time.perf_counter() # 记录开始时间
    # mp.Process：创建进程对象，此时进程还没开始跑！只是对象
    # target=worker：子进程要执行的函数
    # args=(f"P{i}",5_000_000)：传给 worker 的参数，元组形式
    procs = [mp.Process(target=worker, args=(f"P{i}", 5_000_000)) for i in range(4)]
    for p in procs:
        # .start()：真正像操作系统申请创建子进程，开始执行worker函数
        # 四个进程几乎同时启动，分到不同 CPU 核心并行计算
        p.start()
    for p in procs:
        # .join()：主线程阻塞等待这个子进程执行完毕，才继续往下走
        # 主线程在这里停下，等 P0、P1、P2、P3 全部跑完，才打印耗时
        # 如果不写join：主线程会直接跑到print，子进程还在后台慢慢跑，即使结果就错了
        p.join()
    print(f"耗时 {time.perf_counter()-t0:.2f}s")
```

### Process 常用属性/方法

| 成员 | 说明 |
|---|---|
| `p.start()` | 启动(内部调用 `fork`/`spawn`) |
| `p.join(timeout)` | 等待结束，超市不报错只返回 |
| `p.is_alive()` | 是否存活 |
| `p.terminate()` | 发 SIGTERM (**不会清理资源**) |
| `p.kill()` | 发 SIGKILL (3.7+，更暴力) |
| `p.exitcide` | `0` 正常，`-N` 被信号杀，`None` 未结束 |
| `p.daemon` | 守护进程，父进程退出时被终止 |
| `p.name` / `p.pid` | 名称 / 进程号 |

> daemon 进程内不能再创建子进程，会抛 `AssertionError: daemonic processes are not allowed to have children` 。

## 3.3、三种启动方式(必考)

| 方式 | 平台默认 | 原理 | 特点 |
|---|---|---|---|
| `fork` | Linux(<= 3.13) | 复制父进程内存 | 快，但 **多线程下不安全** ，易死锁 |
| `spawn` | Windows、macOS | 全新解释器 + 重新导入模块 | 慢、干净、安全 |
| `forkserver` | linux(3.14+) | fork 一个干净的服务进程再 fork | 兼顾安全与速度 |

```python
import multiprocessing as mp

# mp.get_context(启动方式)：multiprocessing 有 3 中进程启动上下文，可以手动指定，不在用系统默认值
# 调用 get_context(xxx) 拿到一个上下文对象 ctx
# 从同一个 ctx 里创建的 Process / Queue / Pool，全部统一使用这一套启动规则
ctx = mp.get_context("spawn")      # fork / spawn / forkserver
p = ctx.Process(target=f) # 等价于 mp.Process，只不过走 ctx 指定的 spawn 规则创建进程，而不是系统默认上下文
# 进程间通信队列，这个 Queue 是 spawn 上下文下的队列，只能和同 ctx 的进程一起用。
# Queue 底层是跨进程通信，内部会 pickle 序列化数据
q = ctx.Queue()
# 进程池，一次性预开 4 个 worker 进程，全部用 spawn 方式
# 适合批量任务，不用反复手动 start/join，比一个个手动 Process 方便
pool = ctx.Pool(4)
```

### 为什么必须写 `if __name__ == "__main__":`

`spawn` 启动子进程时，子进程会 **重新导入主模块** (`__main__`)。如果建池代码在模块顶层：

```ini
父进程执行 → 建池 → spawn 子进程 → 子进程 import 主模块 → 又执行建池 → 又 spawn …
```

-> 无限递归，报 `RuntimeError: An attempt has been made to start a new process before the current process has finished its bootstrapping phase` ，或直接卡死 / 耗尽内存。

> 结论：任何 `multiprocessing` 代码，池 / 进程的创建一律放在 `if __name__ == "__main__":` 里，函数定义放在外面(子进程要能 import 到)。

## 3.4、进程池

**写法 A：`multiprocessing.Pool` (老 API)**

```python
import multiprocessing as mp

def square(x: int) -> int:
    return x * x

if __name__ == "__main__":
    # with mp.Pool(...) 上下文管理器：退出 with 块时，自动执行 close() + join()，写法简介，推荐
    with mp.Pool(processes=4) as pool:
        # 输入;[0, 1, 2, ..., 9]，分给4个进程并行计算
        # 有序：输出顺序和输入顺序严格对应
        # 阻塞：主线程卡住，全部任务算完才一次性返回完整列表
        # 缺点：会一次性把所有结果存进内存，数据量大时占内存
        print(pool.map(square, range(10)))              # 有序，阻塞，一次性

        # imap 返回迭代器(惰性)，不是一次性列表
        # 有序：和map一样保持输入顺序
        # 惰性：算出来一个，产出一个，不用等全部结束、不用一次性存全部结果，适合超大迭代器，省内存
        # 速度比map略慢一点
        print(list(pool.imap(square, range(10))))       # 有序，惰性，省内存

        # imap_unordered 无序，哪个任务先算完，哪个结果先返回，不在维持输入顺序
        # 惰性迭代，省内存
        # 优先拿到已经完成的结果，不需要等慢任务，吞吐更高
        print(list(pool.imap_unordered(square, range(10))))  # 无序，最先完成先返回

        # starmap 支持多参数版本的map
        # 会把元组里面的值拆开，作为参数传给函数：
        # 普通 map 只能传单参数；多个参数就用 starmap
        print(pool.starmap(pow, [(2, 3), (3, 4)]))      # 多参数

        # apply_async 提交单个任务，异步非阻塞，提交之后主线程不会卡住，继续往下跑
        # 返回一个 AsyncResult 对象
        # .get() 阻塞等待拿结果 timeout=5 代表最多等 5 秒，超时直接抛异常
        r = pool.apply_async(square, (7,))              # 异步单个
        print(r.get(timeout=5))

```

**写法B：`ProcessPoolExecutor(推荐)`**

```python
# 导入 ProcessPoolExecutor 进程执行器(进程池)
# 导入 as_completed 用来遍历已经完成的 future 任务，先做完先拿到
# 导入 os.cpu_count() 获取本机 CPU 核心数，作为最大进程数
from concurrent.futures import ProcessPoolExecutor, as_completed
import os

# work 任务函数
# 输入 x,返回元组 (x, x**2) 。spawn 模式下，这个函数必须在顶层定义，子进程才能找到。
def work(x: int) -> tuple[int, int]:
    return x, x * x

if __name__ == "__main__":
    # 上下文管理器，自动管理进程池：
    # 退出 with 块自动等待所有任务、自动回收进程，不用手动 close/join，非常方便
    # 最大并发进程数 = CPU 核心数量，是 CPU 密集任务常用配置。
    with ProcessPoolExecutor(max_workers=os.cpu_count()) as ex:
        # 1) map：有序、阻塞，和 multiprocessing.pool.map 行为一致，返回迭代器
        print(list(ex.map(work, range(5))))

        # 2) submit + as_completed：谁先完成先处理
        # ex.submit(work, i) 提交单个任务，返回 Future 对象，立即返回、不阻塞主线程
        # 字典 futs：key 是 future，value 是原始参数 i (方便你追溯是哪个任务)
        futs = {ex.submit(work, i): i for i in range(5)}
        # as_completed(futs)：迭代器，哪个 future 先执行完毕，就先 yield 哪一个
        # 输出顺序无需！哪个进程算的快，哪个先打印，对应前面 imap_unordered 的效果
        for fut in as_completed(futs):
            # fut.result() 拿到这个任务的返回值；如果任务抛异常，调用 result() 的时候才会抛出异常
            print(fut.result())
```

|  | `multiprocessing.Pool` | `ProcessPoolExecutor` |
|---|---|---|
| 接口风格 | 自有 API | 与线程池统一 |
| 异常传播 | 较弱 | 标准 (`fut.result()` 抛出) |
| 切换线程/进程 | 要重写 | **改类名即可** |
| 推荐度 | 维护老代码 | 新代码首选 |

**3.11+ 新参数：`max_tasks_per_child`**

长时间运行的池会出现 **内存泄漏累积** (比如Pandas的碎片)。让 worker 处理 N 个任务后重启：

```python
with ProcessPoolExecutor(max_workers=4, max_tasks_per_child=100) as ex:
    ...
```

## 3.5、进程间通信(IPC)

**所有跨进程传递的数据必须可 pickle**：不能传 lambda、局部函数、生成器、打开的文件、socket、数据库连接。

> pickle：python内置的二进制序列化的模块，
> pickling（序列化）：把内存里的 Python 对象转换成二进制字节流（存文件/网络传输）
> unpickling（反序列化）：二进制字节流还原成 Python 对象

| 方式 | 方向 | 适用 | 性能 |
|---|---|---|---|
| `Queue` | 多对多 | 通用任务分发 | 中 |
| `Pipe` | 一对一 | 双向点对点 | 高 |
| `Value` / `Array` | 共享 | 少量标量 / 数组 | 高 |
| `Manager` | 共享 | 任意 Python 对象 (dict / list) | 低 |
| `shared_memory` (3.8+) | 共享 | 大 numpy 数组零拷贝 | 最高 |

## Queue

```python
import multiprocessing as mp

# 生产者
def producer(q: mp.Queue, n: int) -> None:
    for i in range(n):
        # q.put(item, block=True, timeout=None)
        # block=False: 不阻塞，满了直接抛 queue.full ,
        # timeout=3: 阻塞后最多等3秒，还没空位就抛 Full
        # 把对象 i 放入队列，默认阻塞模式, 队列已经满了（元素数量 == maxsize），
        # put() 原地卡住，一直等到队列腾出空位才放进去、函数返回
        q.put(i)

    # 只放入一个 None --这个 None 就是哨兵(sentinel)
    # 约定：None 不是业务数据，是“没有更多数据，可以退出”的信号
    q.put(None)                      # 哨兵，通知结束

# 消费者
def consumer(q: mp.Queue, name: str) -> None:
    # q.get() 默认阻塞调用：队列空的时候，进程停在这里等，不会往下走
    # q.get(block=True, timeout=None)
    # block=False: 空队列直接抛 queue.Empty
    # timeout=0.5: 阻塞后最多等0.5s，拿不到抛 Empty
    # 拿到 None -- 循环条件不成立，函数直接返回，消费者进程正常结束
    while (item := q.get()) is not None:
        print(f"{name} 收到 {item}")

if __name__ == "__main__":
    # mp.Queue是多进程安全的队列，内部自带锁，多个进程 put / get 不会竞争错乱
    # maxsize=10 队列最多缓存 10 个元素,队列满时 put() 阻塞(背压)，队列空时 get() 阻塞。
    q = mp.Queue(maxsize=10)         # maxsize 提供背压

    # 创建一个生产者进程，句柄放进 ps 中
    ps = [mp.Process(target=producer, args=(q, 5))]

    # 创建两个消费者进程，句柄放进 ps 中
    ps += [mp.Process(target=consumer, args=(q, f"C{i}")) for i in range(2)]
    # 注意：只有一个哨兵，两个消费者要发两个
    ...
```

> Queue 的两个经典坑：
> `q.get()` **永久阻塞** —— 生产者崩了没发哨兵。用 `q.get(timeout=5)`。
> `q.empty()` **不可靠** —— 多进程下结果瞬时过期，别用他做循环条件。

## Pipe

```python
import multiprocessing as mp
import os

def child(conn):
    # send(obj): 把对象 pickle 序列化发给管道另一端
    conn.send({"msg": "hello", "pid": os.getpid()}) # os.getpid(): 获得该进程的进程ID

    # 关闭子进程这边的管道端口
    conn.close()

if __name__ == "__main__":
    # duplex=True: 默认，双向，两边既能发(send())也能收(recv())
    # duplex=False: 单向，只能左边发(send())，右边收(recv())
    # parent：父进程持有的端口 ； child_conn：传给子进程的端口
    # multiprocessing.Pipe 管道通信，双工管道
    parent, child_conn = mp.Pipe(duplex=True)

    # 把子端口传给子进程，子进程持有 child_conn
    p = mp.Process(target=child, args=(child_conn,))

    # start() 真正创建操作系统子进程；
    # 调用 start() 之前，只是一个 Python 进程描述对象，没有 OS 进程
    p.start()

    # 阻塞等待，直到管道对面 send 数据过来；拿到之后反序列化，返回对象
    # recv() 是阻塞的，对面没有send，recv()卡死
    # 如果所有发送端都 close 了，在调用 recv() 会抛 EOFError(管道已经关闭，没有更多数据)
    print(parent.recv())

    # 主进程阻塞，等待子进程执行完毕
    p.join()
```

> 注意：`Pipe` 的两端分别给两个进程用，**不要在多个进程间共享同一端**(会有竞态)。且 `send/recv` 要配对，否则死锁。

## Value / Array (共享内存 + 内置锁)

```python
import multiprocessing as mp

def add(v):
    for _ in range(1000):
        # v.get_lock() 获取配套锁，不加锁就会出现竞争
        with v.get_lock():           # 必须加锁，否则丢更新
            v.value += 1  # 临界区：对共享值修改

if __name__ == "__main__":
    # mp.Value / mp.Array 是 multiprocessing 内置的共享内存对象，
    # 跨进程共享（和多线程里普通全局变量不一样，进程之间内存隔离）
    # multiprocessing.Value('i'/'d'/'f'/'b', 初始值, lock=True)
    # 多进程共享内存变量，在主进程和子进程之间共享一个基础类型数值
    # 'i'=int, 'd'=double, 'f'=float, 'b'=char
    # lock=True : 默认，自动附带一个锁，可以使用.get_lock()获取，
    # 如果lock=False 不带锁，需要自己另外传锁进去
    # .value 属性读写
    v = mp.Value("i", 0)

    # multiprocessing.Array(typecode, size_or_initializer, lock=True)
    # 共享内存数组，同质 C 类型的连续数组，和 mp.Value 是一类（共享内存），区别是它存一组数据
    # 'i' = int, 'd' = double, 'f' = float, 'b' = char
    # size_or_initializer: 传数字N，创建长度N，初始值全0；传可迭代对象，用序列初始化，长度自动匹配
    # lock=True 默认，自带锁，可用 arr.get_lock() 获取配套锁；lock=False() 无内置锁
    # 读写操作和列表相同，支持下标和切片
    arr = mp.Array("d", 10)          # 10 个 double

    # 创建四个进程对象，每个进程运行add(v)
    ps = [mp.Process(target=add, args=(v,)) for _ in range(4)]

    # 创建/启动 四个进程，主线程阻塞，等待四个子进程运行完毕
    [p.start() for p in ps]; [p.join() for p in ps]
    print(v.value)                   # 4000
```

### Manager(万能但慢)

```python
import multiprocessing as mp

if __name__ == "__main__":
    # multiprocessing.Manager 进程托管管理器，启动一个单独的管理服务进程，
    # 所有托管对象（dict/list/Lock/Namespace） 都存在这个Manager进程，
    # 其他子进程通过 IPC(进程间通信) 访问、修改它
    # 所管容器之间听顶层赋值，嵌套对象就地修改不会自动同步！

    # 上下文写法，退出 with 块自动关闭 manager 进程，
    # 自动回收资源，等价手动 mgr.shutdown()
    with mp.Manager() as mgr:
        # 子进程修改，所有进程可见
        # d['a'] = 1
        # d['a'] = 2
        # d['b'] = [1, 2]
        # 坑：d['lst'].append(3) 这种内部修改，检测不到，要加锁或者重新赋值
        d = mgr.dict()  # 托管字典

        # lst.append(10)
        # lst[0] = 99
        # 坑：lst[0].append() 嵌套容器内部修改有坑
        lst = mgr.list()  # 托管列表

        # 跨进程同步锁，用法和 mp.Lock() 一样：
        # lock.acquire(block=True, timeout=None): 获取锁，默认阻塞：拿不到锁就卡在这里等待
        # acquires(block=False) 非阻塞，拿不到直接返回False，不卡住
        # lock.release(): 释放锁，把锁还给别的进程 / 线程。没拿到锁就调用 release() 抛异常
        # with lock:
        """
        with lock:
            #临界区
        
        等价于
        
        lock.acquire()
        try:
            # 临界区
        finally:
            lock.release()
        """
        lock = mgr.Lock()  # 托管锁

        # 用来放一堆属性，代替dict，写起来更舒服
        # ns.x = 0
        # ns.name = 'test'
        # print(ns.x)
        ns = mgr.Namespace()  # 托管命名空间(存属性)
```

> Manager 背后是一个 **服务进程**，每次操作都是 IPC + 序列化。只适合低频少量数据。**不要用 Manager 传大数组**。

## 3.6、进程同步原语

和线程的家口几乎一样，但是 **跨进程** 的：

```python
mp.Lock() / mp.RLock() / mp.Semaphore(3) / mp.Event() / mp.Condition() / mp.Barrier(4)
```

语义与 `threading` 完全一致，只是作用域从“线程间”变成“进程间”。

## 3.7、常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 缺 `__main__` 保护 | Windows 无限建进程 / RuntimeRrror | 加 `if __name__ == "__main__":` |
| 传 lambda | `PicklingError` | 改模块级函数 |
| 以为子进程改了父进程变量 | 父进程值不变 | 用 Queue 回传或 Value |
| 传大 DataFrame | 慢到不如串行 | `shared_memory` / 分块 / 只传路径 |
| 池建在模块顶层 | import 就建池 -> 爆炸 | 放进 `__main__` 或函数里 |
| `daemon=True` + 建子进程 | AssertionError | 去掉 daemon |
| 池里 worker 内存涨 | OOM | `max_tasks_per_child` |
| 子进程里 print 无输出 | 缓冲 | `flush=True` |
| `terminate()` 后资源泄露 | 临时文件/锁残留 | 用 `try/finally` 清理，优先 `join` |

## 3.8、可复用模板

```python
"""CPU 密集任务的多进程模板"""
import os
from concurrent.futures import ProcessPoolExecutor, as_completed

def handle(item: dict) -> dict:
    """必须是模块级函数，参数/返回值必须可 pickle"""
    return {"id": item["id"], "result": sum(range(item["n"]))}

def main(items: list[dict]) -> list[dict]:
    results = []
    with ProcessPoolExecutor(max_workers=os.cpu_count()) as ex:
        futures = {ex.submit(handle, it): it["id"] for it in items}
        for fut in as_completed(futures):
            try:
                results.append(fut.result())
            except Exception as e:
                print(f"任务 {futures[fut]} 失败: {e}")
    return results

if __name__ == "__main__":
    data = [{"id": i, "n": 1_000_000} for i in range(8)]
    print(main(data))
```

## 本节要点

1. 多进程是 CPU 密集的 **唯一** 标准解法（绕GIL）
2. `if __name__ == "__main__":` 不是风格问题，是 **正确性** 问题
3. 优先 `ProcessPoolExecutor` ，别用裸 `Process` 和 `Pool`
4. 跨进程要序列化：小数据 Queue / Pipe，大数据 `shared_memory`
5. 进程数 = `os.cpu_count()`，不要更多

# 四、多线程 `threading`

## 4.1、原理与 GIL 的位置

```text
┌─────────────────── 进程 ───────────────────┐
│  内存（堆/全局变量）  ← 所有线程共享          │
│                                            │
│  ┌─ 线程1 ─┐  ┌─ 线程2 ─┐  ┌─ 线程3 ─┐      │
│  │  栈     │  │  栈     │  │  栈     │     │
│  └────┬────┘  └────┬────┘  └────┬────┘     │
│       └────────────┼────────────┘          │
│              ┌─────┴─────┐                 │
│              │    GIL    │  ← 只有持有者    │
│              └─────┬─────┘     能执行字节码 │
│              ┌─────┴─────┐                 │
│              │  解释器   │                  │
│              └───────────┘                 │
└────────────────────────────────────────────┘
```

**关键理解**：GIL 是“执行权令牌”。线程拿到令牌才能跑 Python 代码；遇到 I/O 或 sleep 时主动交出令牌，其他线程才有机会跑。

**推论**：多线程的加速 **完全依赖“交出令牌的时机”**。全是纯计算的线程不会主动交（只在 5ms 间隔被动交出），所以只是白付切换成本。

## 4.2、最小示例

```python
import threading, time

def download(name: str, sec: float) -> None:
    print(f"{name} 开始")
    time.sleep(sec)              # 模拟 I/O，释放 GIL
    print(f"{name} 完成")

t0 = time.perf_counter()
ths = [threading.Thread(target=download, args=(f"T{i}", 1), name=f"worker-{i}")
       for i in range(8)]
for t in ths: t.start()
for t in ths: t.join()
print(f"耗时 {time.perf_counter()-t0:.2f}s")   # ≈1s
```

### Thread 常用成员

| 成员 | 说明 |
|---|---|
| `t.start()` / `t.join(timeout)` | 启动 / 等待 |
| `t.is_alive()` | 是否运行中 |
| `t.daemon` | 守护线程，主线程退出即被杀 |
| `t.name` | 线程名（调试用） |
| `threading.current_thread()` | 当前线程对象 |
| `threading.active_count()` | 活跃线程数 | 
| `threading.enumerate()` | 所有线程列表 |
| `threading.get_index()` | 线程 ID (数字) |
| `t.kill()` | **不存在，线程无法被强制杀死** |

> **Thread 没有 kill**。想让线程停，只能靠共享标志位 (`Event`) 让它自己退出。`daemon=True` 是被强杀，可能在持锁 / 写文件时被杀 -> 数据不一致。

## 4.3、线程安全：`+=` 为什么不是原子的

```python
counter += 1
```

对应的字节码是三步：

```text
LOAD_GLOBAL  counter      # ① 读
LOAD_CONST   1
BINARY_OP    +=           # ② 加
STORE_GLOBAL counter      # ③ 写
```

线程可能在 ① 和 ③ 之间被切换走，另一个线程读到旧值 -> **更新丢失**

```python
import threading

counter = 0
lock = threading.Lock()

def bump():
    global counter
    for _ in range(100_000):
        with lock:
            counter += 1

ths = [threading.Thread(target=bump) for _ in range(4)]
[t.start() for t in ths]; [t.join() for t in ths]
print(counter)     # 加锁：稳定 400000；不加锁：通常 < 400000
```

哪些操作天然是原子的？
CPython 里 **单条字节码** 天然原子 (因为 GIL)：

- `lst.append(x)`、`lst.pop()`、`dict[k] = v`、`dict.get(k)`
- `x = y`（引用赋值）
- 读取单个属性

**不原子** 的(必须加锁)：

- `x += 1`、`x -= 1`、`d[k] += 1`
- `if k not in d: d[k] = ...` (check-then-act)
- `list[i] = list[i] + 1`
- 任何“读--改--写”组合

> 但 **不要依赖“单条字节码原子”来写代码** ：实现细节会变，且 free-threaded Python 下不成立。**有共享可变状态就加锁**。

## 4.4、同步原语全览

| 原语 | 语义 | 典型场景 | 备注 |
|---|---|---|---|
| `Lock` | 互斥，一次一个 | 保护计数器 | 非重入，同线程二次获取会死锁 |
| `RLock` | 可重入互斥 | 递归函数加锁 / 一个方法调另一个加锁方法 | 内部记 owner + count |
| `Semaphore(n)` | 最多 n 个同时进入 | 限并发(连接池、限速) | 可 `release()` 超发 |
| `BoundedSemaphore` | 同上，但超发报错 | 防 Bug | 推荐用于资源池 |
| `Event` | 一个/多个线程等信号 | 优雅退出、启动同步 | `set/clear/wait/is_set` |
| `Condition` | 条件等待 | 生产者-消费者 | 配合 `wait/notify/notify_all` | 
| `Barrier(n)` | 等 n 个线程都到齐 | 分阶段并行计算 | `wait()` 返回到达序号 |

### Lock 的正确姿势

```python
lock = threading.Lock()

# ✅ 用 with，异常也能释放
with lock:
    do_something()

# ❌ 手动 acquire/release，中间抛异常就死锁
lock.acquire()
do_something()
lock.release()
```

### 死锁四条件与破解

| 条件 | 破解 |
|---|---|
| 互斥 | 尽量不用锁(不可变数据、消息传递) |
| 持有并等待 | 一次性申请所有锁，或 `acquire(timeout=)` |
| 不可剥夺 | `acquire(timeout=1)` 超时放弃并回滚 |
| 循环等待 | `全局固定加锁顺序` (最有效) |

```python
# 固定顺序：永远先锁 id 小的
def transfer(a, b, amount):
    first, second = (a, b) if id(a) < id(b) else (b, a)
    with first.lock, second.lock:
        ...
```

### Event: 优雅退出

```python
import threading

stop = threading.Event()

def worker():
    while not stop.is_set():
        print("working...")
        stop.wait(1)          # ★ 比 sleep 好：可以被set立刻唤醒并返回 True
    print("退出")

t = threading.Thread(target=worker, daemon=False)
t.start()
# ... 主逻辑
stop.set()
t.join()
```

### Semaphore: 限流

```python
# 初始 3 个令牌，最多 3 个并发，令牌不够阻塞
sem = threading.Semaphore(3)

def task(i):
    with sem:
        # 进入 with 时，自动 acquire 取令牌，取不到就阻塞

        print(f"task {i} 执行")
        time.sleep(0.5)  # 模拟工作

        # 离开 with 时，自动 release：还令牌
```

## 4.5、生产者-消费者：`queue.Queue`

线程间 **不要自己造轮子**，用线程安全的 `queue.Queue`

```python
import queue, threading, time

q: queue.Queue = queue.Queue(maxsize=10)    # maxsize 提供背压

def producer():
    for i in range(20):
        q.put(i)                            # 满了阻塞
    for _ in range(NUM_CONSUMERS):          # 每个消费者一个哨兵
        q.put(None)

def consumer(name: str):
    while True:
        item = q.get()
        if item is None:
            break
        print(f"{name} 处理 {item}")
        time.sleep(0.1)

NUM_CONSUMERS = 3
threading.Thread(target=producer, daemon=True).start()
cs = [threading.Thread(target=consumer, args=(f"C{i}",)) for i in range(NUM_CONSUMERS)]
[c.start() for c in cs]; [c.join() for c in cs]
```

### `queue.Queue` API

| 方法 | 说明 |
|---|---|
| `put(item, block=True, timeout=None)` | 满则阻塞 |
| `put_nowait(item)` | 满则抛 `queue.Full` |
| `get(block=True, timeout=None)` | 空则阻塞 |
| `get_nowait()` | 空则抛 `queue.Empty` |
| `task_done()` | 标记一个任务完成 (配 `join` ) |
| `join()` | 阻塞直到所有任务 `task_done` |
| `qsize()` | 近似大小 (不要用于逻辑判断) |

> `q.rmpty()` 和 `qsize()` 在并发下 **不可靠**，不要用来写 `while not q.empty():` 。正确做法是用哨兵(`None`) 或 `join()`。

## 4.6、线程池

```python
# 导入线程池ThreadPoolExecutor，负责创建和复用线程
# 导入 as_completed, 一个迭代器工具，作用是 按“完成顺序”产出结果，而不是 按提交顺序
# 导入 requests, 第三方 HTTP 库， pip install requests
from concurrent.futures import ThreadPoolExecutor, as_completed
import requests

def fetch(url: str) -> tuple[str, int]:
    # requests.get() 是阻塞调用--
    # 这个函数会停在这里等服务器响应，这正是它能被多线程加速的原因(等待时会释放 GIL)
    r = requests.get(url, timeout=10)

    # len(r.content)：r.connect 是响应体的长度 bytes, len 拿到字节数(不是字符数)
    return url, len(r.content)

# 生成 20 个URL,每个都让 httpbin 延迟一秒才返回，用来模拟满请求
# httpbin.org 是一个真正的网址，一个全能 HTTP 请求与响应测试服务
urls = [f"https://httpbin.org/delay/1?i={i}" for i in range(20)]

# 创建线程池，最多同时跑10个任务，线程名前缀变为 'fetch', 例 'fetch_0'
with ThreadPoolExecutor(max_workers=10, thread_name_prefix="fetch") as ex:
    # ex.submit(fetch, u) 把任务丢进线程池，立刻返回一个 Future 对象，不等它执行完
    # 用字典把 Future->url 存起来，后面出错时能反查是哪个 URL
    futures = {ex.submit(fetch, u): u for u in urls}

    # 按 完成顺序遍历
    for fut in as_completed(futures):
        try:
            # fut.result()拿返回值。如果任务里抛了异常，异常会在这里被重新抛出
            url, size = fut.result()
            print(f"✓ {url} {size}B")
        except Exception as e:
            print(f"✗ {futures[fut]}: {e}")
```

### 默认参数

| `max_workers` | `min(32, os.cpu_count() + 4)` |
| `thread_name_prefix()` | `"ThreadPoolExecutor"` |
| `initializer` / `initargs` | `None` (3.7+) |

> **max_workers 怎么定：** I/O 密集可以远大于核数(如 50-200)；但注意目标服务的承受能力、文件句柄、内存。**先测再调**，不要拍脑袋 |

## 4.7、常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 不加锁改共享变量 | 结果偏小、随即丢数据 | `with lock:` |
| 用多线程跑 CPU 计算 | 比单线程还慢 | 换多进程 |
| `q.empty()` 做循环条件 | 提前退出、漏数据 | 用哨兵 `None` |
| `get()` 无超时 | 永久卡住 | `timeout=` |
| `daemon=True` 写文件 | 文件损坏一半 | 非 `daemon` + `Event` 退出 |
| 线程数爆了内存 | OOM | 用池，别裸建 Thread |
| `t.kill()` | AttributeError | 不存在，用标志位 |
| 子线程 print 不输出 | 主线程先退出了 | `join()` |
| 全局变量 + 多线程 | 数据错乱 | 尽量无状态函数 |

## 4.8、可复用模板

```python
"""I/O 密集 + 阻塞库的线程池模板"""
from concurrent.futures import ThreadPoolExecutor, as_completed
import logging  # 记日志

# __name__ 在作为模块导入时是模块名(比如：mytool.fetcher),直接运行脚本时是 "__main__"
# 用 __name__ 建 logger 是库代码的标准做法：日志会带上源模块，调用方可以按模块名单独调级别。
# 好处：你不需要关心日志输出到哪、什么格式--那是应用层用 logging.basicConfig() 决定的。
log = logging.getLogger(__name__)


def handle(item):
    return item * 2

# items : 待处理的任务集合，可以是 list、生成器、任何可迭代对象
# max_workers=20 : 默认，最多20个线程同时干活
def run(items, max_workers=20):
    # results: 存结果 ，errors: 存失败的 (任务, 异常) 对
    results, errors = [], []

    # 创建线程池，最多可以同时创建 max_workers 个线程，“按需创建”
    with ThreadPoolExecutor(max_workers=max_workers) as ex:
        # 把handle(it)调用放进线程池队列，立即返回一个 Future 对象
        futures = {ex.submit(handle, it): it for it in items}

        # 按完成顺序遍历
        for fut in as_completed(futures):
            try:
                # 无异常放进results
                results.append(fut.result())
            except Exception as e:
                # log.exception()它会让 logging 自动抓取当前正在处理的异常（sys.exc_info()），把 Traceback (most recent call last): ... 一起写进日志。
                # "failed: %s", futures[fut]是 log.exception() 的延迟格式化写法，
                # 日志调用时只创建 LogRecord ，msg 和 args 分开保存
                # 只有真正要输出时，才在 getMessage() 里执行 msg % args
                # 如果级别被过滤时，_log()直接返回，连 LofRecord 都不创建
                log.exception("failed: %s", futures[fut])
                errors.append((futures[fut], e))
    return results, errors
```

### 本节要点

1. 多线程的收益全部来自“等待时交出 GIL”。
2. `+=` 不原子；check-then-act 不原子；GIL 不保护逻辑
3. 有共享可变状态 -> 加锁；能无状态就无状态
4. 线程间通信用 `queue.Queue`，不要共享 list + 锁
5. 线程**不能被杀**，只能协商瑞出(Event)。
6. 池的 `max_workers` 默认 `min(32, cpu+4)` 。

# 五、协程 `asyncio`

## 5.1、演进史(理解 why)

| 时代 | 方案 | 问题 |
|---|---|---|
| Py2 | 回调 / 线程 | 回调地狱 / GIL + 内存 |
| 2.5 | `yield` 生成器 | 只能往外送值 |
| 3.3 | `yield from` (PEP 380) | 可委托子生成器，协程雏形 |
| 3.4 | `asyncio` + `@coroutine` | 写法丑 |
| 3.5 | `async` / `await` (PEP 492) | 语法定型 |
| 3.6 | 异步生成器 / 异步推导 | 生态完善 |
| 3.7 | `asyncio.run()` | 统一入口 |
| 3.11 | `TaskGroup` / `asyncio.timeout()` | 结构化并发 |
| 3.12 | `eager_task_factory`、`asyncio.Runner` | 性能、可复用循环 |

> **核心洞察**：`async / await` 本质是 **生成器的语法糖**。`await x` 会把当前函数的执行状态挂起，把控制全交还给事件循环。所谓 “协程”，就是 **能被暂停和恢复的函数**。

## 5.2、三个必须记住的事实

1. `async def` 定义的函数，**调用它不执行任何代码**，只返回一个协程对象。
2. 写成对象必须被 `await` ，或包装成 `Task` 被调度，才会运行。
3. 必须有 **事件循环** 驱动，入口是 `asyncio.run()`。

```python
import asyncio

coro = some_async_func()      # ← 此处什么都没有发生
print(type(coro))             # <class 'coroutine'>

asyncio.run(coro)             # 真正开始执行
```

```python
import asyncio

# 演示：调用不等于执行
async def demo():
    print("被执行了")

c = demo()
print("还没执行")      # 先打印
asyncio.run(c)        # 才打印"被执行了"
```

## 5.3、事件循环：它到底在做什么？

```python
# 伪代码
while True:
    就绪任务 = 取出所有可以继续跑的任务
    for task in 就绪任务:
        task.step()          # 跑到下一个 await 就返回

    if 所有任务都在等 I/O:
        events = selector.select(timeout)   # epoll/IOCP，阻塞在这里
        唤醒对应的任务，标记为就绪
```

关键点：

- 事件循环是 **单线程** 的。
- `await` 处让出控制权，不是 **阻塞**。
- 底层用 `select` / `epoll` (Linux) / `kqueue` (macOS) / `IOCP` (Windows) 做 I/O 多路复用。

### 心智模型

```python
事件循环 = 一个"调度员" + 一堆"可暂停的任务"

任务A: 跑 → await(等网络) → 挂起（把控制权还给调度员）
调度员: 好，那我先跑任务B
任务B: 跑 → await(等磁盘) → 挂起
调度员: 网络好了！唤醒A ...
```

## 5.4、并发编排：五种方式

```python
import asyncio, time

async def work(i: int) -> int:
    await asyncio.sleep(1)
    return i * i
```

### 串行--错误示范

```python
async def serial():
    return [await work(i) for i in range(5)]      # 5 秒！
```

`await` 只是“等待这一个”，不会并发。这是 **初学者第一大坑**。

### `gather`--最常用

```python
async def use_gather():
    return await asyncio.gather(*(work(i) for i in range(5)))   # 1 秒

# 注意 !!! 参数要解包，直接传 list 会报错
# ❌ asyncio.gather([work(i) for i in range(5)])
# ✅ asyncio.gather(*(work(i) for i in range(5)))
```

`gather` 的异常行为:

```python
# 默认：第一个异常抛出，其余任务继续跑（可能泄漏）
await asyncio.gather(a(), b())

# 收集所有异常，不中断
results = await asyncio.gather(a(), b(), return_exceptions=True)
```

### `TaskGroup`--3.11+推荐

```python
async def use_taskgroup():
    async with asyncio.TaskGroup() as tg:
        tasks = [tg.create_task(work(i)) for i in range(5)]
    return [t.result() for t in tasks]        # 1 秒

# 结构化并发：任一任务失败 → 其余全部自动取消
# 异常以 ExceptionGroup 抛出，用 except* 捕获
async def safe():
    try:
        async with asyncio.TaskGroup() as tg:
            tg.create_task(may_fail())
    except* ValueError as eg:
        print("值错误:", eg.exceptions)
```

### `as_completed`--谁先完成先处理

```python
async def use_as_completed():
    out = []
    for fut in asyncio.as_completed([work(i) for i in range(5)]):
        out.append(await fut)          # 返回顺序 = 完成顺序
    return out
# 实测输出顺序：[4, 3, 2, 1, 0]（i 越大 sleep 越短）
```

### `wait`--细粒度控制

```python
done, pending = await asyncio.wait(
    [asyncio.create_task(work(i)) for i in range(5)],
    timeout=0.5,
    return_when=asyncio.FIRST_COMPLETED,   # ALL_COMPLETED / FIRST_EXCEPTION
)
for t in pending:
    t.cancel()
```

### 编排方式对比

| **API** | 返回 | 异常行为 | 何时用 |
|---|---|---|---|
| `await` 循环 | 列表 | 立即中断 | 几乎不要 |
| `gather` | 结果列表 | 首个抛出，其余继续 | 老代码、需要 `return_exceptions` |
| `TaskGroup` | 任务列表 | **失败取消全部** | 新代码首选 |
| `as_completed` | 迭代器 | 逐个处理 | 需要边完成边处理 |
| `wait` | (done, pending) | 不抛 | 需要超时 / 部分取消 |

## 5.5、三大控制：限流、超时、取消

### 限流：`Semaphore`

```python
sem = asyncio.Semaphore(10)          # 最多 10 个并发

async def fetch(i):
    async with sem:
        await asyncio.sleep(0.1)
        return i

async def main():
    return await asyncio.gather(*(fetch(i) for i in range(1000)))
```

> 不要一次开 1 万个协程直接打开目标站。**Semaphore 是生产环境必加项**。

### 超时：`asyncio.timeout` (3.11+)

```python
async def main():
    try:
        async with asyncio.timeout(3):        # 3 秒整体超时
            await long_task()
    except TimeoutError:
        print("超时")

# 老写法
result = await asyncio.wait_for(long_task(), timeout=3)
```

区别：`asyncio.timeout` 是 **上下文管理器**，能覆盖内部多个 `await`，且支持嵌套和动态修改(`timeout.reschedule()`)。

### 取消

```python
task = asyncio.create_task(long_task())
await asyncio.sleep(1)
task.cancel()
try:
    await task
except asyncio.CancelledError:
    print("已取消")
    # 注意：可以在这里做清理，但通常应该 raise 继续传播
```

> `CancelledError` **在 3.8+ 继承自** `BaseExceotion`，不是 `Execption` 。所以 `except Exception:` 抓不到它--这是故意的。永远不要写裸 `except:` ，会吞掉取消信号导致任务无法结束。

#### 取消的正确姿势

```python
async def safe_cleanup():
    try:
        await do_work()
    except asyncio.CancelledError:
        await cleanup()      # 可以做清理
        raise                # ★ 必须重新抛出
```

## 5.6、asyncio 的同步原语

单线程内不需要“互斥”，但 **仍需要“协作式”的同步** (因为 await 会让出)

| 原语 | 用途 |
|---|---|
| `asyncio.Lock` | 保护“await 之间”的临界区 |
| `asyncio.Semaphore` | 限流 |
| `asyncio.Event` | 协作间通知 |
| `asyncio.Condition` | 条件等待 |
| `asyncio.Queue` | 生产者-消费者 (最常用) |

```python
# asyncio.Lock 存在的意义：await 之间状态可能被改
lock = asyncio.Lock()
balance = 0

async def withdraw(n):
    global balance
    async with lock:
        if balance >= n:            # 检查
            await asyncio.sleep(0)  # ★ 这里会切换走！
            balance -= n            # 修改
```

### asyncio.Queue 生产者-消费者

```python
import asyncio

async def producer(q: asyncio.Queue, n: int):
    for i in range(n):
        await q.put(i)              # 满了会挂起
    await q.put(None)

async def consumer(q: asyncio.Queue, name: str):
    while (item := await q.get()) is not None:
        print(name, "got", item)
        q.task_done()

async def main():
    q = asyncio.Queue(maxsize=2)
    async with asyncio.TaskGroup() as tg:
        tg.create_task(producer(q, 5))
        tg.create_task(consumer(q, "A"))

asyncio.run(main())
```

## 5.7、铁律：不要再协程里写阻塞调用

事件循环是单线程的。**一个阻塞调用会让所有协程停摆**。

```python
async def bad():
    time.sleep(1)                    # ❌ 全循环停 1 秒
    requests.get(url)                # ❌ 全循环停到响应返回
    open("big.bin").read()           # ❌ 磁盘阻塞
    hashlib.pbkdf2_hmac(...)         # ⚠️ CPU 密集（C 层释放 GIL 但会占满循环）
    while True: pass                 # ❌ 直接卡死
```

### 三种正确解法

```python
import asyncio, time

async def good():
    # ① 换异步版本（最优）
    await asyncio.sleep(1)
    async with httpx.AsyncClient() as c:
        await c.get(url)

    # ② 丢到线程池（阻塞库，3.9+）
    text = await asyncio.to_thread(requests.get, url)

    # ③ 丢到进程池（CPU 密集）
    loop = asyncio.get_running_loop()
    result = await loop.run_in_executor(None, cpu_heavy, 10**7)
```

### 对照表：同步 -> 异步

| 同步 | 异步替代 |
|---|---|
| `time.sleep(n)` | `await asyncio.sleep(n) |
| `requests` | `httpx.AsyncClient` / `aiohttp` |
| `open()` | `aiofiles.open()` |
| `pymysql` / `psycopg2` | `asyncmy` / `asyncpg` |
| `redis` | `redis.asyncio` |
| `pymongo` | `motor` |
| `subprocess.run` | `asyncio.create_subprocess_exec` |
| `ThreadPoolExecutor` | `asyncio.to_thread` |

## 5.8、常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 循环里 `await` | 变串行，没变快 | `gather` / `TaskGroup` | 
| `gather([...])` 不解包 | `TypeError` | `gather(*(...))` |
| 用 `time.sleep` | 所有任务一起卡 | `asyncio.sleep` | 
| 用 `requests` | 同上 | `httpx` / `to_thread` |
| 协程没 `await` | `RuntimeWarning: coroutine was never awaited` | 检查是否漏 `await` |
| `create_task` 不保存引用 | 任务莫名消失 | 存 list 或用 TaskGroup |
| `asyncio.run()` 嵌套 | `RuntimeError: asyncio.run() cannot be called from a running event loop` | 用 `await main()` |
| `get_event_loop()` | 3.10+ 报 `There is no current event loop` | 用 `asyncio.run()` / `get_running_loop()` |
| Lock 跨循环复用 | `RuntimeError: is bound to a different event loop` | 每次 `run()` 内新建 |
| 没有限流 | 被封 IP / 打挂服务 | `Semaphore` |
|吞掉 `CancelledError` | 任务无法取消 | 只捕 `Exception` ，捕获后 `raise` |
| `async with` 忘了 | 资源泄露 | `aiohttp` / `httpx` 必须 `async with` |

## 5.9、可复用模板：并发爬虫

```python
"""asyncio 并发请求模板：限流 + 超时 + 重试 + 异常隔离"""
import asyncio
import httpx

URLS = [f"https://httpbin.org/delay/1?i={i}" for i in range(20)]
CONCURRENCY = 5
TIMEOUT = 10
RETRIES = 3

async def fetch(client: httpx.AsyncClient, url: str, sem: asyncio.Semaphore) -> str | None:
    async with sem:
        for attempt in range(RETRIES):
            try:
                r = await client.get(url, timeout=TIMEOUT)
                r.raise_for_status()
                return r.text
            except Exception as e:
                if attempt == RETRIES - 1:
                    print(f"✗ {url}: {e}")
                    return None
                await asyncio.sleep(2 ** attempt)     # 指数退避

async def main():
    sem = asyncio.Semaphore(CONCURRENCY)
    async with httpx.AsyncClient() as client:
        async with asyncio.TaskGroup() as tg:
            tasks = [tg.create_task(fetch(client, u, sem)) for u in URLS]
        results = [t.result() for t in tasks]
    print(f"成功 {sum(r is not None for r in results)}/{len(URLS)}")

if __name__ == "__main__":
    asyncio.run(main())
```

### 本节要点

1. `async def` 只是“定义”，调用不执行；必须 `await` 或 `create_task`。
2. 事件循环单线程；`await` = 主动让出，不是阻塞。
3. 循环里逐个 `await` 时串行，必须用 `gather` / `TaskGroup`。
4. 新代码用 `TaskGroup`；需要“边完成边处理”用 `as_completed`
5. **绝不能在写协程里用阻塞调用**，这是“协程没变快”的第一原因。
6. `CancelledError` 是 `BaseException`，捕获后要 `raise`。

## 7.2、混合架构(真实项目标配)

**多进程 + 进程内协程** = CPU 并行 + I/O 高并发。

```python
import asyncio, httpx
from concurrent.futures import ProcessPoolExecutor

async def crawl_batch(urls: list[str]) -> list[int]:
    sem = asyncio.Semaphore(20)
    async with httpx.AsyncClient() as client:
        async def one(u):
            async with sem:
                r = await client.get(u, timeout=10)
                return len(r.text)
        return await asyncio.gather(*(one(u) for u in urls))

def worker(urls: list[str]) -> list[int]:
    return asyncio.run(crawl_batch(urls))          # 子进程内跑事件循环

def split(lst, n):
    k = (len(lst) + n - 1) // n
    return [lst[i:i + k] for i in range(0, len(lst), k)]

if __name__ == "__main__":
    urls = [f"https://example.com/{i}" for i in range(400)]
    with ProcessPoolExecutor(max_workers=4) as ex:
        results = list(ex.map(worker, split(urls, 4)))
    print(sum(len(r) for r in results))
```

## 7.3、反模式 (不要这么做)

| 反模式 | 问题 | 正确做法 |
|---|---|---|
| 多线程跑纯 CPU 计算 | GIL，比串行还慢 | 多进程 |
| 为 I/O 任务开 20 个进程 | 内存爆炸，收益不高 | 线程池或协程 |
| 1 万个裸 `Thread` | 内存耗尽 | 线程池 |
| 无限协程打第三方 API | 被封 IP / 打卦对方 | `semaphore` 限流 |
| `asyncio` 里调 `requests` | 事件循环阻塞 | `httpx` / `to_thread` | 
| 用 `Manager` 传大数组 | IPC 序列化极慢 | `shared_memory` |
| 全局变量 + 多线程 | 数据竞态 | 锁 / 无状态 / 消息队列 |
| `except:` 裸捕获 | 吞掉 `CancelledError` | `except Exception:` |
| 用 `q.empty()` 判结束 | 多进程下不可靠 | 哨兵 `None` |

## 8.1、标准压测脚本

```python

import asyncio, time, os
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor

# ============ 测试任务 ============
def cpu_task(n: int) -> int:
    s = 0
    for i in range(n):
        s += i * i
    return s

def io_task(sec: float) -> float:
    time.sleep(sec)
    return sec

async def aio_task(sec: float) -> float:
    await asyncio.sleep(sec)
    return sec

# ============ 计时工具 ============
def bench(label, fn, *args):
    t0 = time.perf_counter()
    fn(*args)
    print(f"{label:<28} {time.perf_counter()-t0:6.2f}s")

# ============ CPU 密集 ============
N, WORKERS = 20_000_000, 4

def run_serial_cpu():
    [cpu_task(N) for _ in range(WORKERS)]

def run_thread_cpu():
    with ThreadPoolExecutor(WORKERS) as ex:
        list(ex.map(cpu_task, [N] * WORKERS))

def run_process_cpu():
    with ProcessPoolExecutor(WORKERS) as ex:
        list(ex.map(cpu_task, [N] * WORKERS))

# ============ I/O 密集 ============
COUNT, SEC = 20, 0.5

def run_serial_io():
    [io_task(SEC) for _ in range(COUNT)]

def run_thread_io():
    with ThreadPoolExecutor(COUNT) as ex:
        list(ex.map(io_task, [SEC] * COUNT))

def run_async_io():
    async def main():
        await asyncio.gather(*(aio_task(SEC) for _ in range(COUNT)))
    asyncio.run(main())

if __name__ == "__main__":
    print(f"CPU 核数 = {os.cpu_count()}, 任务数 = {WORKERS}\n")
    bench("CPU 串行", run_serial_cpu)
    bench("CPU 4 线程", run_thread_cpu)
    bench("CPU 4 进程", run_process_cpu)
    print()
    bench(f"I/O 串行 ({COUNT}×{SEC}s)", run_serial_io)
    bench(f"I/O {COUNT} 线程", run_thread_io)
    bench(f"I/O {COUNT} 协程", run_async_io)
```

## 9.1、案例：批量下载 + 限流 + 重试(三种实现)

```python
# ============ ① 线程池版（阻塞库，改动最小）============
from concurrent.futures import ThreadPoolExecutor, as_completed
import requests

def crawl_thread(urls, workers=20):
    def get(u):
        for i in range(3):
            try:
                r = requests.get(u, timeout=10)
                r.raise_for_status()
                return len(r.content)
            except Exception:
                if i == 2:
                    return None
    with ThreadPoolExecutor(workers) as ex:
        return {u: f.result() for u, f in
                ((u, ex.submit(get, u)) for u in urls) for f in [f]}
```

```python
# ============ ② 协程版（资源最省，推荐）============
import asyncio, httpx

async def crawl_async(urls, concurrency=50):
    sem = asyncio.Semaphore(concurrency)
    async with httpx.AsyncClient() as client:
        async def one(u):
            async with sem:
                for attempt in range(3):
                    try:
                        r = await client.get(u, timeout=10)
                        r.raise_for_status()
                        return len(r.content)
                    except Exception:
                        if attempt == 2:
                            return None
                        await asyncio.sleep(2 ** attempt)
        async with asyncio.TaskGroup() as tg:
            tasks = [tg.create_task(one(u)) for u in urls]
        return [t.result() for t in tasks]
```

```python
from concurrent.futures import ProcessPoolExecutor
import os

def _get(u):
    import requests

def crawl_process(urls):
```

## 9.2、案例：生产者-消费者(三线程模型)

```python
"""下载 → 解析 → 入库，三段流水线"""
import queue, threading, time

q1, q2 = queue.Queue(10), queue.Queue(10)
STOP = object()

def downloader(urls):
    for u in urls:
        time.sleep(0.1)                 # 模拟下载
        q1.put(f"data-of-{u}")
    q1.put(STOP)

def parser():
    while (raw := q1.get()) is not STOP:
        time.sleep(0.05)                # 模拟解析
        q2.put(raw.upper())
    q2.put(STOP)

def saver():
    while (item := q2.get()) is not STOP:
        time.sleep(0.02)                # 模拟入库
        print("saved", item)

urls = [f"u{i}" for i in range(10)]
threads = [
    threading.Thread(target=downloader, args=(urls,)),
    threading.Thread(target=parser),
    threading.Thread(target=saver),
]
for t in threads: t.start()
for t in threads: t.join()
```

> 要点：**每个阶段独立队列 + 哨兵逐级传递**。`maxsize` 让快阶段自动等慢阶段(背压)。

## 9.3、案例：进程池处理大文件 (分块)

```python
from concurrent.futures import ProcessPoolExecutor
import os

def process_chunk(path_with_range):
    path, start, end = path_with_range
    with open(path, "rb") as f:
        f.seek(start)
        data = f.read(end - start)
    return len(data), sum(data)          # 占位：实际做计算

if __name__ == "__main__":
    path = "big.bin"
    size = os.path.getsize(path)
    n = os.cpu_count()
    chunk = size // n
    ranges = [(path, i * chunk, (i + 1) * chunk if i < n - 1 else size)
              for i in range(n)]
    with ProcessPoolExecutor(n) as ex:
        print(list(ex.map(process_chunk, ranges)))
```

> 关键：**传“路径 + 偏移量”而不是“数据本身”，避免把几十 GB 序列化过去。

## 10.1、通用

| 现象 | 原因 | 解法 |
|---|---|---|
| 多任务比单任务还慢 | 任务太小，调度开销 > 收益 | 加批量、减少任务数 |
| 内存爆炸 | 并发数 x 单任务内存 | 限并发 / 流式处理 |
| 程序不退出 | 有非 daemon 线程 / 进程 | `join()` 或 `Event` 通知 |
| 结果顺序乱 | 用了 `as_completed` / `imap_unordered` | 需要顺序就 `map` |
| 日志交错 | 多线程 / 进程写同一文件 | 用 `logging` + `QueueHandler` |

## 10.2、多进程专属

| 现象 | 解法 |
|---|---|
| Windows 无限建进程 | `if __name__ == "__main__":` |
| `PicklingError` | 模块级函数；大数据用 `shared_memory` |
| 父进程看不到子进程的修改 | 用 `Queue` / `Value` 回传 |
| `daemonic processes are not allowed to have childrens` | 去掉 `daemon=True` |
| 子进程 print 无输出 | `flush=True` 或 `-u` |
| 池泄露内存 | `max_tasks_per_child` |
| fork 下多线程死锁 | 改 `spawn`:`mp.get_context('spawn')` |

| 现象 | 解法 |
|---|---|
| 计数器结果偏小 | `with lock:` |

| 无法停止线程 | `Event` 标志位 (没有 kill) |

|---|---|

| 任务莫名消失 | `create_task` 结果存 list 或用 `TaskGroup` |

# 十一、面试高频问答

## Q1: Python 多线程能利用多核吗？

不能(默认构建)。CPython 有 GIL，同一时刻只有一个线程执行字节码。多线程只在 I/O 等待 (释放 GIL) 时有并发收益。CPU 并行要用多进程。

## Q2: 既然有 GIL ，为什么还需要 Lock？

GIL 保证单条字节码原子，但业务逻辑是多条字节码组成的。`counter += 1` 是 “读-改-写”三步，中间可能被切换。check-then-act 同样不安全。

## Q3: GIL 什么时候释放？

1. I/O 阻塞时
2. `time.sleep`
3. C 扩展主动释放 (numpy / hashlib / zlib / sqlite3)
4. 每执行 N 条字节码后周期性让出 (`sys.getswitchinterval()` 默认 5ms)

## Q4: 多进程和多线程怎么选？

CPU 密集 -> 多进程；
I/O 密集 -> 多线程或协程；
需要隔离 / 容错 -> 多进程
需要大量共享数据 -> 线程/协程

## Q5: 协程和线程的本质区别？

线程是 **抢占式** (OS 决定何时切换)，协程是 **协作式** (代码在 `await` 处主动让出)。协程切换在用户态，开销小 1-2 个数量级，但 **一个阻塞调用会卡死整个事件循环** 。

## Q6: `asyncio` 是不是多线程？

不是。`asyncio` 是单线程事件循环 + 协作式调度。多线程是并发的另一种实现。

## Q7: `gather` 和 `TaskGroup` 的区别？

`gather`: 一个任务失败时抛异常，但其余任务 **继续运行** (可能泄露)。`TaskGroup`: 任一失败 **自动取消其余所有**，异常以 `ExceptionGroup` 抛出，用 `except*` 捕获。新代码推荐 `TaskGroup` 。

## Q8: 进程间通信有哪些方式？

`Queue`(多对多)、`Pipe`(一对一)、`Value` / `Array` (共享内存)、`Manager` (任意对象，慢)、`shared_memory`(大数组零拷贝)、`socket`、文件、数据库、消息队列(Redis / RabbitMQ / Kafka) 。

## Q9: 为什么多进程传参必须 pickle？

进程内存独立，参数必须序列化成字节流通过 IPC 传给子进程。lambda、局部函数、打开的文件、数据库连接都不可 pickle。

## Q10: 什么是结构化并发？

任务的生命周期被严格限制在一个作用域内 (`async with TaskGroup`)，离开作用域时所有子任务必然结束(完成或取消)，不会泄露。类比 `with` 管理资源。

## Q11: `CancelledError` 为什么继承 `BaseException`？

防止 `except Exception:` 误吞取消信号，导致任务无法终止。设计上要求显示处理或让它继续传播。

# Q12: 多进程一定比多线程快吗？

不。进程创建/销毁成本高(ms级)，数据要序列化。任务太碎、数据太大时，多进程可能比串性还慢。**要测**。

## 13.1、一行代码模板

```python
from concurrent.futures import ThreadPoolExecutor

from concurrent.futures import ProcessPoolExecutor
with ProcessPoolExecutor() as ex: r = list(ex.map(fn, items))

import asyncio
async def m(): return await asyncio.gather(*(fn(i) for i in items))
asyncio.run(m())

sem = asyncio.Semaphore(10)
async def one(x):

# 异步 + 超时
async with asyncio.timeout(5): await fn()

# 阻塞函数转异步
await asyncio.to_thread(blocking_fn, arg)

# 线程安全计数器
with lock: counter += 1

stop = threading.Event(); stop.set(); t.join()

from multiprocessing import shared_memory
```
